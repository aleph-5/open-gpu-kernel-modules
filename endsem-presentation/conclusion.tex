\section{Future Work \& Conclusion}

\begin{frame}{Key Strengths and Limitations}
\begin{columns}[T]

\column{0.48\textwidth}
\textbf{Strengths}
\begin{itemize}[<+->]
    \scriptsize
    \item \textbf{Zero application footprint:} tracking is entirely kernel-side; no recompile, no runtime library, no hardware extensions required
    \item \textbf{Exact semantics:} first-write-wins with nanosecond timestamps gives a roughly ordered write identity per page
    \item \textbf{Deterministic lifecycle:} ISR flush + TLB drain at every boundary ensures no write straddles an epoch; all correctness tests pass including concurrency and lifecycle-race suites
    \item \textbf{No fixed overhead floor:} cost is strictly proportional to write-fault density - compute-bound kernels (GEMM $\leq$16\,GB: 13--26\%) pay negligible cost
    \item \textbf{O(1) query overhead:} delta-mode \texttt{query\_dump} swaps a pointer; querying more frequently does not add measurable cost
\end{itemize}

\column{0.48\textwidth}

\textbf{Limitations}
\begin{itemize}[<+->]
    \scriptsize
    \item \textbf{Write-heavy workloads are expensive:} overhead scales with write-fault density - 4K-stride reaches $+1688\%$ at 40\,GB; the system is unsuitable for write-intensive kernels with large working sets
    \item \textbf{Single-session:} only one PID may hold an active session (\texttt{EBUSY} on concurrent start)
    \item \textbf{Oversubscription amplification:} at $\geq$32\,GB, GEMM's regime shift spikes overhead to 207--267\% across all backends, exposing a coupling between UVM eviction pressure and tracking cost
    \item \textbf{Manual backend selection:} the \texttt{dirty\_tracking\_hint} requires the caller to know the access pattern; no automatic dispatch is implemented, could have a dynamic management
\end{itemize}

\end{columns}
\end{frame}

\begin{frame}{Future Work}
\begin{itemize}[<+->]
    \item \textbf{Automatic backend selection:} PTX store instructions reveal sequential vs.\ random write patterns; this can drive automatic dispatch to the correct backend, replacing the manual \texttt{dirty\_tracking\_hint}
    \item \textbf{Write-reachable VA space narrowing:} NVVM IR alias analysis can identify \texttt{cudaMallocManaged} arguments; at \texttt{start}/\texttt{resume}, only reachable VA blocks need downgrading, reducing barrier latency at large working-set sizes
    \item \textbf{Write-heat aware eviction:} Epoch-frequency counts from successive dumps can bias UVM's LRU scorer to keep write-hot pages on-device and evict clean pages, reducing re-fault frequency under memory pressure
    \item \textbf{Adaptive cutover for live migration:} Insert counts from \texttt{dirty\_ds\_stats} expose the per-epoch write rate; a migration controller can defer \texttt{query\_cutover} until the write rate drops below transfer bandwidth, improving pre-copy convergence
    \item \textbf{Dirty ratio as a scheduling signal:} Pages dirtied per epoch divided by allocation size indicates compute phase; checkpoint and migration controllers can adapt inter-round intervals entirely from user space via the existing procfs interface
\end{itemize}
\end{frame}

\begin{frame}{Conclusion}
\begin{itemize}[<+->]
    \item The GPU fault path is a natural and sufficient instrumentation point. Dirty tracking does not require hardware extensions, compiler changes, or application modification
    \item Forcing pages to \texttt{READ\_ONLY} and recording on the first write fault is the right primitive: it gives exact, timestamped, per-page write identity at the cost only of writes, not reads
    \item Strong lifecycle guarantees matter more than raw performance. The determinism of \texttt{start}, \texttt{pause}, \texttt{resume}, and cutover is what makes the system trustworthy enough to drive live migration and checkpointing
    \item Overhead is fundamentally proportional to write-fault density; compute-bound kernels that amortise faults over long runtimes see negligible cost, which is exactly the workload profile that benefits most from dirty tracking
\end{itemize}
\end{frame}
